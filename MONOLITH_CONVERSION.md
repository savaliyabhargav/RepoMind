# Split RepoMind backend monolith into true microservices

**Status as of 2026-09-20: Phases 0-6 complete.** `backend/` is now 6 independent Spring Boot services (`auth-service`, `repo-ingestion-service`, `explain-diagram-service`, `analysis-service`, `ai-provider-service`, plus the `common` library module) — the monolith and its temporary `legacy-monolith` strangler shell are both gone. Only Phase 7 (full docker-compose regression / manual smoke test) remains.

Phase 6 (wiring + cleanup) — **done**. `docker-compose.yml`'s single `backend` block was replaced with 5 service blocks (ports 8081-8085), each pointed at the others via docker-network hostnames (`AUTH_SERVICE_URL`, `INGESTION_SERVICE_URL`, `AI_PROVIDER_SERVICE_URL` env vars); Postgres gets a `postgres-init/01-create-service-databases.sql` init script creating `auth_db`/`repo_db`/`explain_db`/`analysis_db` on first boot. Each new service needed its own `Dockerfile` — since every module's `pom.xml` inherits from the reactor parent via `<relativePath>../pom.xml</relativePath>`, each Dockerfile's build **context is the whole `backend/` reactor root** (not just its own module dir, unlike the old single-module Dockerfile), running `mvn -pl <module> -am spring-boot:run`. `frontend/vite.config.js`'s single `/api` proxy became 5 path-matched rules (most-specific-first: the two `/repo/*/files/*/explain` and `/repo/*/overview` shapes route to explain-diagram-service before the general `/repo` rule catches the rest) — each rule strips the `/api` prefix before forwarding, since none of the new services kept the old `context-path: /api` setting. `legacy-monolith` deleted entirely (from the Maven reactor and the filesystem). Added a disabled `@SpringBootTest` context-load smoke test per real service (matching the original `BackendApplicationTests` pattern — needs Docker infra to actually run).

Full verification after Phase 6: backend reactor `BUILD SUCCESS` across all 6 modules, 73 real tests passing + 5 disabled context-load tests (78 total, 0 failures) — accounts for the original 74/0/1 baseline (the 1 original skipped test was `legacy-monolith`'s own smoke test, now replaced 1-for-1 per service). Frontend: 41/41 passing, completely unaffected as expected (it mocks the `api` axios instance, never makes real HTTP calls in tests). `docker compose config` validates the new compose file with no errors.

Remaining: Phase 7 — bring the full stack up for real and confirm the actual user journey (login → ingest → explain → analyze) still works end-to-end through the new service boundaries.

## Context

RepoMind's backend is currently one Spring Boot module (`com.repomind.backend`, single Maven artifact, single `application.yml`, single Postgres database `repomind`). The goal is to break it into genuinely independent microservices — separate deployables, separate databases, network calls instead of in-process method calls — specifically because the class count has made the codebase hard to navigate, and each resulting service should be small enough to understand on its own. True microservices were chosen over a lower-risk modular-monolith alternative after weighing the tradeoff: some of the project's most-touted engineering (the `REQUIRES_NEW` cache-write race safety, the canonical-repo wait-then-takeover, DB-confirmed Kafka acks) currently relies on being inside one transaction/process; splitting means re-deriving those guarantees across a network boundary where needed, or accepting they don't apply to the newly-separated pieces.

Full codebase inventory (endpoints, entities, FKs, Kafka topics, JWT mechanics, docker-compose, frontend call sites, test layout) was gathered via three research passes. Key findings that shape the design below:

- **Domain graph:** `User`→`RefreshToken`; `User`→`Repo`→`CanonicalRepo`→`FileNode` (`FileDependency` exists but is dead code, never injected anywhere); `Repo`+`User`→`Analysis`→`AnalysisStage`; `User`+`Analysis`→`AiCallLog`. `FileNode` has **no content column** — raw file content is fetched live from GitHub per-request via `GitHubContentClient` using the user's stored OAuth token, never persisted.
- **Cross-domain leaks today:** `FileNodeRepository`/`RepoRepository` are injected directly into `AnalysisPipelineService` and into `FileExplainService`/`RepoOverviewService` (explain domain) — both domains read repo/file data they don't own, and `AnalysisPipelineService` also **writes** `FileNode.roleSummary` via a custom update query. These become real inter-service calls (one of them a cross-service write) once split.
- **AI layer is clean:** `AiProviderRouter`/`AiProviderClient` + DTOs have zero entity/JPA coupling — a strong candidate to extract as its own AI gateway microservice, and the lowest-risk first extraction.
- **JWT is already service-split-ready:** RS256 via `RsaKeyConfig`, signing needs the private key (auth-service only), validation needs only the public key (`certs/public_key.pem`) — `JwtAuthFilter` + `JwtService.isTokenValid/extractUserUuid` is a small, cleanly reusable unit for every other service.
- **`AiCallLog` is written from exactly one place** (`AnalysisPipelineService.persistAiCallLog`) — the explain domain's AI calls are currently *not* logged anywhere. This is a pre-existing gap, not something this migration should silently "fix" by adding new writes from explain-diagram-service — preserving current behavior means only analysis-service keeps writing `ai_call_logs`.
- **`RetrievalService` is a pure disabled stub** (no DB/vector access at all) and `chat_sessions`/`chat_messages`/`share_links` tables have zero endpoints anywhere — out of scope for this split beyond just relocating their (currently unused) migrations.
- **Frontend never talks to multiple hosts today** — everything goes through Vite's dev proxy (`/api` → one backend). The frontend `Dockerfile` only runs `vite dev` (no nginx/production build stage), so extending the *existing* Vite proxy with multiple path-based targets is the lowest-risk way to front 5 services without introducing a brand-new gateway component that has to be built and debugged from scratch. A dedicated gateway service can replace this later with zero frontend code changes.

## Target service boundaries

| Service | Port | Owns tables | Owns code |
|---|---|---|---|
| **auth-service** | 8081 | `users`, `refresh_tokens` | `AuthController`, `AuthService`, `GitHubService`, `JwtService`, `RsaKeyConfig` (both keys), `SecurityConfig`, `User`, `RefreshToken` |
| **repo-ingestion-service** | 8082 | `canonical_repos`, `repos`, `file_nodes`, `file_node_dependencies` | `RepoController`, `GitHubApiClient`, `GitHubUrlParser`, `GitHubRateLimitTracker`, `RepoIngestionProducer`, `IngestionWorker`, `FileNodeBatchWriter`, `KafkaTopicConfig`, `CanonicalRepo`, `Repo`, `FileNode`, `FileDependency` |
| **explain-diagram-service** | 8083 | `file_explain_cache` | `FileExplainController`, `FileExplainService`, `ExplainCacheService`, `RepoOverviewService`, `DiagramGenerationService`, `CodeCondenser`, `GitHubContentClient` (moved here — its only consumer), `FileExplainCache` |
| **analysis-service** | 8084 | `analyses`, `analysis_stages`, `ai_call_logs`, (placeholder) `chat_sessions`, `chat_messages`, `share_links`, `prompt_templates` | `AnalysisController`, `AnalysisPipelineService`, `RetrievalService` (kept as-is, still a stub), `Analysis`, `AnalysisStage`, `AiCallLog` |
| **ai-provider-service** | 8085 | none (stateless) | `AiProviderRouter`, `AiProviderClient` + 3 impls, all AI DTOs. Holds the GROQ/NVIDIA/GEMINI API keys — no other service needs them anymore. |

Plus a small **`common`** Maven module (compiled dependency, not a runtime service) shared by all five: the JWT validation filter + public-key config + `GlobalExceptionHandler` base + a standard internal-API error DTO. This keeps each service independently deployable while not hand-duplicating identical security boilerplate five times.

**Data ownership rule:** every FK that used to cross a table now owned by a different service becomes a plain stored UUID column — no cross-database FK constraints (normal/expected for DB-per-service; referential integrity for those becomes an application-level concern). Concretely: `Repo.userId`, `Analysis.userId`, `AiCallLog.userId`/`analysisId` all drop their `@ManyToOne`/`@JoinColumn` and become plain `UUID` fields.

**New internal (service-to-service only, not gateway-routed) endpoints needed:**
- auth-service: `GET /internal/users/{userId}` (id, username, avatarUrl, plan — used by repo-ingestion-service to validate a user exists on ingest, and by analysis-service the same way), `GET /internal/users/{userId}/github-token` (used by explain-diagram-service to fetch raw file content from GitHub)
- repo-ingestion-service: `GET /internal/repos/{repoId}` (Repo summary incl. canonicalRepoId/owner/name/defaultBranch), `GET /internal/canonical-repos/{id}/files` (FileNode list), `GET /internal/canonical-repos/{id}/files/{fileId}` (single FileNode), `PATCH /internal/files/{fileId}/role-summary` (replaces `AnalysisPipelineService`'s direct `updateRoleSummary` write)
- ai-provider-service: `POST /internal/ai/generate`, `POST /internal/ai/embed` (mirrors `AiProviderClient.generate/embed` signatures, returns the same `AiGenerationResponse`/`AiEmbeddingResponse` shape including usage so callers can still populate `AiCallLog` themselves)

**Database strategy:** one shared Postgres *container* (unchanged in docker-compose), but 5 separate logical databases (`auth_db`, `repo_db`, `explain_db`, `analysis_db`, plus ai-provider-service has none) with separate credentials — real data isolation and independent Flyway history per service, without standing up 5 Postgres containers. Existing local dev data in the single `repomind` DB is not migrated — each new service starts from an empty DB via its own renumbered Flyway migrations (V12's `canonical_repos`/`repos`/`file_nodes` cross-table migration moves whole into repo-ingestion-service since all three tables belong there). This means locally-ingested test repos need to be re-ingested once after the split; this is called out explicitly as the one accepted "reset" rather than a silent data-loss surprise.

**Routing:** extend `frontend/vite.config.js`'s existing `proxy` block with multiple path-matched rules instead of one, pointing at each service's docker-compose hostname:port — `/api/auth` → auth-service, `/api/repo/*/files/*/explain` and `/api/repo/*/overview` → explain-diagram-service (registered before the general rule), `/api/repo` → repo-ingestion-service, `/api/analyses` → analysis-service. Frontend code (`authService.js`, `repoService.js`) needs **zero changes** — same relative paths, same single `/api` baseURL.

## Implementation phases (each ends in a runnable, tested checkpoint)

**Phase 0 — Maven skeleton.** Convert `backend/pom.xml` into a reactor parent (`packaging: pom`, `<modules>`), create `common/` and 5 empty service module directories each with their own `pom.xml` (inherit parent, own `spring-boot-maven-plugin` execution) and a placeholder `@SpringBootApplication` class. Verify: `mvn -f backend/pom.xml clean install` succeeds with 6 trivial modules. **← currently in progress, blocked (see status note below)**

**Phase 1 — ai-provider-service** (safest, zero entity coupling). Move `AiProviderRouter`, `AiProviderClient` + 3 impls, AI DTOs, `WebClientConfig`. Add `/internal/ai/generate` and `/internal/ai/embed` REST endpoints wrapping the router. Own `application.yml` with just the AI provider keys. Verify: `POST /internal/ai/generate` against a real provider key returns the same shape `HealthController.aiHealthCheck()` used to check manually.

**Phase 2 — auth-service.** Move `AuthController`, `AuthService`, `GitHubService`, `JwtService`, `RsaKeyConfig`, `SecurityConfig`, `User`, `RefreshToken`, migrations V1/V2. Build the `common` module's JWT-validation-only filter here first (it's the reference implementation other services copy from). Verify: full login → refresh → logout cycle works against the frontend, cookies still set correctly.

**Phase 3 — repo-ingestion-service.** Move `RepoController`, ingestion Kafka pipeline (`IngestionWorker`, `FileNodeBatchWriter`, `RepoIngestionProducer`, `KafkaTopicConfig`), `GitHubApiClient`/`GitHubUrlParser`/rate-limit classes, `CanonicalRepo`/`Repo`/`FileNode`/`FileDependency`, migrations V3/V4/V5/V12. Add the 4 internal endpoints. Wire the one new outbound call (`GET /internal/users/{userId}` to auth-service) into `RepoController`'s ingest validation. Verify: ingest a fresh repo end-to-end, confirm tree populates in the frontend exactly as before, Kafka topics/consumers behave identically (redelivery, canonical-repo race handling unchanged — this logic doesn't move, just its container).

**Phase 4 — explain-diagram-service.** Move `FileExplainController`, `FileExplainService`, `ExplainCacheService`, `RepoOverviewService`, `DiagramGenerationService`, `CodeCondenser`, `GitHubContentClient`, `FileExplainCache`, migration V13. Rewrite `FileExplainService`/`RepoOverviewService`'s direct `FileNodeRepository`/`RepoRepository` calls as HTTP calls to repo-ingestion-service's internal endpoints; rewrite the `User.getGithubToken()` read as a call to auth-service's `/internal/users/{userId}/github-token`; rewrite the direct `AiProviderRouter` call as a call to ai-provider-service. Verify: explain a file and load the repo overview through the frontend, confirm cache hit/miss behavior and Mermaid output are unchanged from before the split.

**Phase 5 — analysis-service.** Move `AnalysisController`, `AnalysisPipelineService`, `RetrievalService`, `Analysis`, `AnalysisStage`, `AiCallLog`, migrations V6/V7/V8/V9/V10/V11 (placeholder ownership for the unused chat/share tables). Rewrite the `Repo`/`FileNode` reads and the `updateRoleSummary` write as calls to repo-ingestion-service; rewrite direct AI calls as calls to ai-provider-service, still writing `AiCallLog` locally from the returned usage data. Verify: run the full 7-stage pipeline against a test repo, confirm stage outputs match pre-split behavior.

**Phase 6 — wiring + cleanup.** Update `docker-compose.yml` (5 backend service blocks replacing the single `backend` block, each with its own DB env vars and port mapping; Postgres container unchanged, gets an init step creating the 4 extra databases). Update `frontend/vite.config.js` proxy rules. Delete the now-empty old monolithic package structure. Redistribute the 9 existing backend test files into their new modules per the mapping already confirmed (auth: `AuthServiceTest`/`JwtServiceTest`; repo-ingestion: `RepoControllerTest`/`GitHubRateLimitTrackerTest`/`GitHubUrlParserTest`/`IngestionWorkerTest`; explain: `CodeCondenserTest`; ai-provider: `AiProviderRouterTest`); replace `BackendApplicationTests` with 5 minimal per-service context-load tests.

**Phase 7 — full regression.** Run every service's test suite + the unchanged frontend Vitest suite. Manual smoke test of the full user journey through the frontend: login → ingest a repo → view tree → explain a file → view repo overview → run an analysis → view stages. Confirm nothing observable to the user changed.

Phases proceed sequentially, running the relevant tests/smoke checks at the end of each one, flagging immediately if anything breaks rather than pushing forward.

## Verification

- Backend: `cd backend && ./mvnw -f pom.xml clean install` after each phase (reactor build across whatever modules exist so far); each service also independently runnable via `./mvnw -pl <service> spring-boot:run`.
- Frontend: `cd frontend && npx vitest run` after Phase 6 (should be unaffected — it mocks the `api` axios instance, not real HTTP, so no changes expected here at all).
- End-to-end: `docker compose up --build` after Phase 6, then manually walk the flow in a browser: GitHub login → paste a repo URL → watch ingestion complete → open a file's diagram → open the repo overview → start an analysis and watch stages complete — same as the pre-split app.
- Explicit non-goal: this migration does not add new features, change the AI failover/caching/condensing logic, or touch the Kafka producer/consumer semantics — only their process/deployment boundary changes.
